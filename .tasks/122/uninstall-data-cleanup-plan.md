# Безопасная очистка при удалении приложения

Статус: план для ревью, production-код ещё не изменён. Issue: https://github.com/mesilov/bitrix24-php-lib/issues/122. База: `dev`, исходный коммит `4741133`.

## Цель и границы

Реализовать в библиотеке проверенный uninstall и очистку принадлежащих ей credentials/данных. Вызывающее приложение подключает собственную очистку через явный контракт. В этот PR не входят изменения CRM2Spreadsheet, запуск очистки существующих production-данных, слияние и выпуск версии.

## Основание

- Порядок публикации, редакция 18.09.2026, §3.А: https://apidocs.bitrix24.ru/market/preparing-to-publish/publication-requirements.html.
- ONAPPUNINSTALL: https://apidocs.bitrix24.ru/api-reference/common/events/on-app-uninstall.html. Проверено через официальный Bitrix24 MCP: событие содержит `application_token`, `member_id`, `CLEAN=0/1`. OAuth-токены не передаются, API после удаления недоступно. События не доставляются до завершения установки.
- `CLEAN` выражает выбор очистки данных приложения. Порядок не описывает явно исключение для CLEAN=0: документировать этот предел, не обещать соответствие произвольного хранения без подтверждения модерации.

## Обнаруженное поведение

`src/ApplicationInstallations/UseCase/Uninstall/Handler.php` ищет установку по application token, а аккаунты — по входящему member ID, без явной проверки их связи; токен включён в логи. Сущности `ApplicationInstallation` и `Bitrix24Account` при uninstall меняют статус, сохраняя credentials. `ApplicationSettings/UseCase/OnApplicationDelete/Handler.php` помечает настройки удалёнными. Методы `delete` Doctrine-репозиториев установки и аккаунта фактически выполняют `save`.

## Целевое поведение

1. Проверить application token и соответствие member ID найденной установке до любого изменения. Контекст очистки строить из серверных сущностей, не из произвольных входящих значений. Домен не использовать как самостоятельное основание удаления.
2. Добавить в uninstall-команду явный признак очистки, соответствующий CLEAN. Принимать только допустимые значения на границе; библиотечный контракт типизирован. Не превращать отсутствующее/ошибочное значение в полную очистку. Описать изменение публичного контракта и миграцию вызывающего кода.
3. Для обоих значений CLEAN удалить сохранённые OAuth credentials удалённой установки. Выбрать физическое удаление связанных аккаунтов вместо подстановки фиктивного AuthToken: текущий SDK требует непустой объект из `getAuthToken()`. Проверить связанные FK и переходы повторной установки; не менять существующий repository.delete незаметно для остальных сценариев, выделить явно названную операцию очистки.
4. При CLEAN=1 физически удалить библиотечные пользовательские настройки, включая soft-deleted, и связанные пользовательские сведения, принадлежащие только этой установке. Общие контактные/партнёрские сущности не удалять каскадно: проверить другие ссылки и документировать владение.
5. Ввести контракт обработчика очистки приложения с контекстом installation ID, member ID и CLEAN, без credentials. Приложение обязано отключить свои сессии и задания при любом uninstall; полная очистка пользовательских данных вызывается с CLEAN=1. Библиотека не управляет Google и таблицами выгрузок самостоятельно.
6. Для очистки в общей БД использовать одну транзакцию: ошибка обработчика откатывает удаление и сохраняет возможность проверенного повтора. Во время сбоя вызывающее приложение должно блокировать дальнейшие действия установки; отдельно описать этот обязательный порядок. Внешние действия приложения записываются им в собственную транзакционную очередь, а не выполняются внутри транзакции библиотеки. Не объявлять их завершёнными при одной записи в очередь.
7. После успешного выполнения сохранять минимальную техническую отметку удаления: идентификатор поколения установки, хеш application token для распознавания повторов и результат. Без исходного application/access/refresh token и персональных полей. Отметка не даёт права выполнять действия над новой установкой. Не называть её полной анонимизацией; описать назначение и срок обслуживания.
8. Повтор успешно завершённого удаления — безопасный no-op. Старый token после переустановки не удаляет новые аккаунты/настройки. При неизвестном или несовпадающем контексте никаких изменений. Учесть конкурирующие uninstall/reinstall, блокируя соответствующие записи в транзакции.
9. Удалить application token из логов изменяемых сценариев. Не переносить его в исключения, события или контекст обработчика приложения.

## Изменения и проверки совместимости

- `src/ApplicationInstallations/UseCase/Uninstall/{Command,Handler}.php`: входной контракт, проверка контекста, orchestration.
- `src/ApplicationInstallations/Services/`: контекст и контракт очистки приложения, координатор транзакции; конкретные имена согласовать при ревью плана.
- `src/ApplicationInstallations/Infrastructure/Doctrine/` и `src/Bitrix24Accounts/Infrastructure/Doctrine/`: явные операции физической очистки, изоляция установки и блокировки.
- `src/ApplicationSettings/Infrastructure/Doctrine/` и `UseCase/OnApplicationDelete/`: очистка всех принадлежащих установке записей при CLEAN=1. Существующий soft-delete не выдавать за физическое удаление.
- Маппинги и миграции: минимальная техническая отметка, порядок FK; проверить фактический актуальный SDK-контракт перед изменениями. Не расширять зависимости без необходимости.
- Сохранить совместимые доменные события или явно описать изменение порядка/доступности удалённых сущностей. Учитывать, что `Flusher` отправляет события после flush, но не обеспечивает надёжную доставку после сбоя процесса: критичную очистку не строить только на подписчике события.
- Обновить `src/ApplicationInstallations/Docs/application-installations.md`, документацию настроек, README и CHANGELOG в текущем формате без нового Unreleased. Пример интеграции показывает CLEAN, обработчик приложения, повтор и транзакционную очередь внешних действий.

## Приёмочные сценарии

1. Корректный uninstall с CLEAN=0: credentials действительно отсутствуют после перечитывания БД; политика оставшихся настроек описана явно.
2. CLEAN=1: отсутствуют credentials и библиотечные пользовательские настройки, включая ранее soft-deleted; обработчик приложения получает доверенный контекст.
3. Чужой/пустой token, несовпадающий member ID, token A + member B: нет удаления, flush или вызова очистки приложения.
4. Повтор, старое событие после reinstall, несколько пользователей портала, другой портал и конкурентные события: новое поколение и чужие данные сохраняются.
5. Сбой обработчика/БД на каждой стадии: нет ложного успеха, повтор возможен; новая установка не используется для завершения старой очистки.
6. Логи и исключения не содержат исходных credentials. Вызовы API отсутствуют. Работают новая установка и повторная установка после очистки.
7. Unit-тесты проверяют контракты и отказы; functional-тесты перечитывают реальную тестовую БД и проверяют FK, удаление и rollback. Сначала воспроизвести регрессии, затем исправить.

## Порядок выполнения

После одобрения плана реализовать код библиотеки в этом PR. По локальному maintainer-skill явное одобрение плана нужно до изменения production-кода. Интеграцию приложения выполнять отдельной задачей после ревью библиотечного PR.

Проверки последовательно и только через Makefile: `make lint-all`, `make test-unit`, `make test-functional`; затем `git diff --check`. Перед functional подтвердить отдельную тестовую БД библиотеки. Для текущего PR только с планом тесты не запускать, проверить diff и содержимое коммита. PR остаётся draft до реализации и успешных проверок.
