# Удаление приложения и очистка данных

## Проверка события

Основание: [Порядок публикации, §3.А](https://apidocs.bitrix24.ru/market/preparing-to-publish/publication-requirements.html) и [ONAPPUNINSTALL](https://apidocs.bitrix24.ru/api-reference/common/events/on-app-uninstall.html).

После удаления API Битрикс24 уже недоступно. Обработчик не вызывает REST, OAuth verifier или profile. Он находит установку по входящему `application_token` и сверяет `member_id` с локальным master-аккаунтом. Входящий домен не используется как основание удаления. Неизвестный token или несовпадающий member ID — успешный возврат без изменений. По одному member ID удалять данные нельзя.

`Command::fromEvent()` принимает явно заданный CLEAN: только `0`, `1`, `"0"`, `"1"`. Отсутствие флага, boolean, массив и неоднозначные строки отклоняются. Передавайте исходные POST-поля без преобразования `(bool)` — строка `"false"` не должна стать разрешением очистки. При ручном создании команды четвёртый аргумент `bool $clean` обязателен.

## Что удаляется

| Данные | CLEAN=0 | CLEAN=1 |
| --- | --- | --- |
| OAuth access/refresh credentials и аккаунты портала | Физически удаляются | Физически удаляются |
| Исходный application token | Стирается | Стирается |
| Старая установка | Удаляется после обработчика приложения | Удаляется после обработчика приложения |
| Настройки, включая soft-deleted | Сохраняются под старым installation ID | Физически удаляются |
| Журнал библиотеки для installation ID | Сохраняется | Физически удаляется |
| Контакты, принадлежащие только этой установке | Сохраняются | Удаляются при отсутствии других ссылок |
| Общие контакты и контакты с partner ID | Сохраняются | Сохраняются как общие сущности |
| Данные приложения, Google, задания, сессии | Обязательный обработчик приложения | Обязательный обработчик приложения |

CLEAN=0 отражает выбор пользователя сохранить данные приложения, но не является подтверждённым исключением из требований публикации. Допустимую политику хранения нужно согласовать с модерацией. Сохранённые настройки автоматически не привязываются к новой установке: перенос требует отдельной проверенной политики приложения. Данные в собственных таблицах, внешних хранилищах, резервных копиях и общие контакты регулируются политикой их владельца; библиотека не объявляет их удалёнными.

## Подключение

```php
use Bitrix24\Lib\ApplicationInstallations\Infrastructure\Doctrine\UninstallationStore;
use Bitrix24\Lib\ApplicationInstallations\Services\Uninstall\ApplicationDataCleanerInterface;
use Bitrix24\Lib\ApplicationInstallations\UseCase\Uninstall\Command;
use Bitrix24\Lib\ApplicationInstallations\UseCase\Uninstall\Handler;

// $applicationDataCleaner — обязательная реализация ApplicationDataCleanerInterface приложения.
// Она использует ту же БД/connection, что и $entityManager.
$handler = new Handler(
    new UninstallationStore($entityManager),
    $applicationDataCleaner,
    $logger,
    $eventDispatcher,
);
$handler->handle(Command::fromEvent($request->request->all()));
// Здесь HTTP-контроллер возвращает 200, в том числе для неизвестного токена/повтора.
```

`ApplicationDataCleanerInterface::clean(UninstallationContext $context)` получает только доверенные `installationId`, `memberId`, `clean`; исходных credentials в контексте нет. Всегда отключайте сессии и задания конкретного installation ID. При `clean=true` удаляйте собственные пользовательские данные и сохранённые credentials внешних сервисов. Не удаляйте всё по member ID: во время повтора там может быть уже другая установка.

Внешние действия записывайте в собственную транзакционную очередь на той же connection; выполняйте отдельным обработчиком без обращения к удалённому приложению Битрикс24. Запись в очередь означает лишь принятие внешней работы, а не её фактическое завершение. В этой очереди обеспечьте свою идемпотентность и изоляцию installation ID. Обработчик не должен выполнять commit/rollback общей транзакции или сохранять входящий application token.

## Транзакции, ошибки и повторы

1. Первая транзакция блокирует найденную установку и аккаунты, проверяет отсутствие конкурирующего текущего поколения, удаляет OAuth-аккаунты, переводит установку в `deleted`, стирает исходный application token и записывает `Uninstallation`. Это состояние фиксируется до вызова пользовательского обработчика.
2. Вторая транзакция блокирует запись удаления, вызывает обработчик приложения, очищает библиотечные данные и ставит время завершения. При ошибке все изменения этой транзакции откатываются. Первая транзакция остаётся зафиксированной: credentials не восстанавливаются.
3. При ошибке возвращается `UninstallationFailedException` без upstream exception/секретов; HTTP-адаптер должен отдать неуспешный статус и обеспечить повтор события. Запись `completed_at_utc IS NULL` показывает незавершённую очистку. После rollback нужен новый EntityManager и новый handler — прежний закрыт. Нельзя отвечать успешным завершением при этой ошибке.
4. Повтор с тем же token/member ID продолжает старую операцию. CLEAN берётся из первоначальной записи, а не из нового запроса. Завершённый повтор — no-op; callback повторно не вызывается. Старая операция никогда не удаляет аккаунты нового поколения: они удаляются только на первой стадии, до создания записи повтора.

Вызов требует отдельного чистого UnitOfWork без внешней транзакции. При незаписанных посторонних изменениях обработчик отказывает до действий; он не должен их случайно закоммитить. Внутри приложения любой worker/API перед действием проверяет активную установку. Удалённая/отсутствующая установка и отсутствие её credentials запрещают действия даже до завершения callback. Запись пользовательских аккаунтов и переустановка должны учитывать эту блокировку; не сохраняйте авторизацию из устаревшего контекста после uninstall.

Запись повтора хранит SHA-256 application token и member ID, installation ID, первоначальный CLEAN и время. Она не содержит исходных токенов, домена, профиля или member ID. Эти хеши — технические псевдонимы, а не заявление о полной анонимности. Периодически удаляйте только завершённые записи по принятому сроку хранения; например, через 30 дней после завершения. Незавершённые записи не удалять до расследования/повтора. После удаления завершённой отметки поздний повтор становится неизвестным событием и также ничего не удаляет. Для повтора pending-операции нужен исходный запрос с token/member ID: одних хешей недостаточно для его восстановления; организуйте безопасную доставку/повтор на входе.

## Миграция и совместимость

Перед подключением нового handler добавьте таблицу через миграции приложения. Пример PostgreSQL приведён в [uninstall-schema.sql](uninstall-schema.sql); XML mapping включён в `config/xml` библиотеки. Сначала обновите схему, затем DI/контроллер. Автоматическая очистка существующих данных при миграции не выполняется.

Важные изменения контракта:

- `Uninstall\Command` требует CLEAN; используйте `fromEvent` для входящих POST-данных.
- Вместо старых repositories/Flusher handler получает `UninstallationStoreInterface`, обязательный обработчик данных приложения, logger и event dispatcher. Библиотека не предоставляет молчаливый пустой cleaner.
- Старые `ApplicationInstallationUninstalledEvent` / `Bitrix24AccountApplicationUninstalledEvent` из этого handler заменены на `ApplicationUninstallationCompletedEvent` с installation ID и CLEAN после фиксации очистки. Перенесите критические подписчики в cleaner. Новое событие — уведомление без гарантии доставки при падении процесса; ошибка подписчика логируется безопасно и не отменяет уже завершённую очистку. Это не транзакционная очередь.
- Существующие сценарии reinstall и `Bitrix24Accounts\UseCase\Uninstall` не превращаются автоматически в физическую очистку. Последний меняет только статусы аккаунтов и не должен использоваться как HTTP entrypoint для ONAPPUNINSTALL. Аналогично `ApplicationSettings\UseCase\OnApplicationDelete` остаётся отдельным soft-delete use case.
- У библиотечных связей UUID-поля скалярные; фактические FK вызывающего приложения надо проверить отдельно. FK на OAuth-аккаунт не должен мешать первой транзакции; модель приложения должна хранить привязку к installation ID. Собственные ссылки на установку/контакт удаляет cleaner в той же транзакции перед удалением библиотечных записей.
- Для старой удалённой установки без записи `Uninstallation` событие — no-op. Ретроочистка старых данных выполняется отдельной миграцией/операцией после определения их владельца.

## Защита конкурентных операций

Реализация lifecycle-lock требует PostgreSQL. `Install`, `OnAppInstall`, создание пользовательского аккаунта и обе стадии uninstall берут общую транзакционную advisory-блокировку `member:<memberId>` через `LifecycleLock`. Она автоматически освобождается при commit/rollback. `Bitrix24Accounts\UseCase\InstallStart\Command` теперь требует восьмой аргумент `applicationInstallationId`; после захвата блокировки handler проверяет, что именно эта установка активна на указанном портале. Запоздавший запрос старого поколения получает `InactiveInstallationException` и не сохраняет credentials.

Все привязки контактов через `Flusher` и физическая очистка берут одинаковые блокировки `contact:<uuid>` в отсортированном порядке. После блокировки Flusher проверяет существование контакта или его создание в текущем UnitOfWork. Это предотвращает привязку к уже удалённому контакту. У скалярных UUID-связей библиотеки нет автоматических FK: собственный код приложения, пишущий ссылки напрямую, обязан использовать тот же протокол или реальные FK своей схемы. Прямой вызов EntityManager.flush в обход Flusher не является безопасным способом изменения этих связей.

Методы lifecycle работают с чистым EntityManager и очищают identity map перед чтением под блокировками, чтобы не использовать устаревшие сущности; не переиспользуйте сохранённые в памяти объекты после вызова. Это также обходит ограничение повторной гидратации уже инициализированных readonly-полей Doctrine. `Install` и `OnAppInstall` выполняют OAuth-проверку внутри блокировки портала до изменения данных, чтобы uninstall не мог пройти между verify и записью credentials. Это увеличивает время удержания lock до сетевого timeout verifier. Uninstall по-прежнему не делает внешних вызовов. Токен уже удалённого поколения дополнительно отклоняется по хешированной отметке до попытки установки.

Запись настроек и журнала через Flusher использует общую блокировку `installation:<uuid>`. После неё проверяется существование установки и её статус, включая новые установки текущего UnitOfWork: в удалённую/отсутствующую установку записывать данные запрещено. Очистка берёт ту же блокировку до удаления. Поэтому начатая ранее запись либо завершится до очистки и попадёт в неё, либо получит `InactiveInstallationException`. Модули настроек и журнала теперь требуют реальную установку-владельца; произвольный UUID больше не подходит. Общий порядок блокировок — member, installation, contact, внутри каждого набора по возрастанию ключа. Для кода приложения, пишущего собственные installation-owned данные, действует тот же протокол или эквивалентная защита в своей БД.

Проверка состояния под generation lock распространяется также на UPDATE самой установки: устаревший объект не может сохранить контакт после удаления. Повторная вставка installation ID с существующей отметкой удаления запрещена. При переустановке библиотека всегда создаёт новый UUID. Не обновляйте старые отсоединённые объекты установки после lifecycle-операции.
